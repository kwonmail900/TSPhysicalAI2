# TSPhysicalAI2 — 캠퍼스 예측과 ESP32 폐루프 에너지 실습

건물의 일별 에너지 예측을 **운영 예산 → LED·모터 제어 → 전력·회전수 관측 → 계획 수정**으로 연결하는 교육 프로그램입니다. PC만으로 실행하는 시연 모드와 ESP32 실물 모드를 제공합니다.

기본 데이터는 합성 시연 자료입니다. 실제 캠퍼스 원시 자료나 첨부 원고는 저장소에 포함하지 않습니다. 예측은 전주 같은 요일을 사용하는 기준 모델이며, 운영 판단은 규칙과 피드백 제어입니다. **현재 결과를 TSFM·LLM 실행 결과로 표기하지 않습니다.**

## 1. PC 시연부터 실행

Python 3.10 이상이 필요합니다. PC 프로그램은 Python 표준 라이브러리로 실행하며 별도 `pip` 설치가 필요하지 않습니다.

```bash
cd TSPhysicalAI2
python server.py --mode demo --host 127.0.0.1 --port 8765
```

Linux/macOS에서는 설치 환경에 따라 `python3`를 사용합니다. Windows에서는 `start_windows.bat`를 실행합니다. 실행한 PC의 브라우저에서 `http://127.0.0.1:8765`를 엽니다. 종료는 터미널의 `Ctrl+C`입니다.

먼저 예측값과 에너지 환산 계수를 확인하고, 가동 승인 후 조명·모터의 관측값이 어떻게 변하는지 살펴봅니다. 에너지 예산과 작업 시한을 바꾸어도 같은 조명 요구와 목표 회전수를 유지하여 결과를 비교합니다. 시연 모드의 값은 수식으로 생성한 결과이며 실물 계측값이 아닙니다.

## 2. 교육용 부하의 의미

| 구성 | 건물에서 대응하는 의미 | 확인할 결과 |
|---|---|---|
| LED | 최소 서비스 요구가 있는 조명 | 명령한 밝기 비율, 전체 소비전력 |
| 엔코더 모터 | 시한 내 일정 작업량을 완료해야 하는 설비 | 실제 누적 회전수와 완료 여부 |
| INA260 | 한 건물 모형의 합계 부하 계측 | 전압·전류·전력·누적 에너지 |
| ESP32 | 현장 명령 실행·계측·로컬 정지 | 유효한 명령 적용과 상태 보고 |
| Python 운영기 | 다음 날 수요를 운영 예산으로 바꾸는 상위 판단 | 예산·서비스·작업 조건의 조정 |

초기 모형에는 팬을 넣지 않았습니다. 작은 팬만으로 실제 환기량이나 건물 냉난방 성능을 검증하기 어렵고, 조명과 작업 부하만으로도 서로 다른 제약을 비교할 수 있기 때문입니다. 태양광·배터리 실물도 포함하지 않습니다.

## 3. 실물 모드

필수 부품, 배선, ESP32 설정과 단계별 시험은 [하드웨어 안내](docs/HARDWARE.md)를 따릅니다. PC와 ESP32는 같은 실습용 Wi-Fi에 연결합니다.

실물 모드에는 `TSPAI_DEVICE_TOKEN`이 필요합니다. 16자 이상의 임의 토큰을 로컬에서 생성하고, PC의 환경 변수와 ESP32의 로컬 `config.h`에 같은 값을 설정합니다. 토큰 값과 Wi-Fi 비밀번호는 Git에 올리지 않습니다.

```bash
# 로컬 실습용 토큰을 생성하여 현재 터미널에 설정합니다.
export TSPAI_DEVICE_TOKEN="$(python -c 'import secrets; print(secrets.token_urlsafe(24))')"
python server.py --mode hardware --host 0.0.0.0 --port 8765
```

PowerShell에서는 다음과 같이 환경 변수를 설정합니다.

```powershell
$env:TSPAI_DEVICE_TOKEN = python -c "import secrets; print(secrets.token_urlsafe(24))"
python server.py --mode hardware --host 0.0.0.0 --port 8765
```

`0.0.0.0`은 서버가 연결을 받는 바인딩 주소이며 ESP32에 입력할 접속 주소가 아닙니다. 펌웨어에는 PC의 실제 LAN 주소를 설정합니다. 방화벽이 요청을 막으면 해당 실습용 사설 네트워크에서만 포트를 허용합니다. 로컬 HTTP 구성은 외부 공개용 서비스가 아닙니다.

ESP32는 부팅 후 자동으로 모터를 가동하지 않습니다. 유효한 계측과 통신을 확인한 뒤 명시적으로 가동 승인합니다. 오류가 발생한 경우 원인을 해결하고 오류 해제 후 별도로 다시 승인합니다. 통신 복구만으로 재가동된다고 가정하지 않습니다.

기본 실습은 예산 1Wh, 전력 상한 12W, 모터 목표 100RPM·누적 200회전·시한 180초입니다. 이는 시연 시작값이며 실제 장치에 맞게 교정합니다. `새 작업`은 엔코더의 현재 누적값을 기준으로 작업량과 시한을 새로 정하며 소비 에너지는 유지합니다. `실험 초기화`는 가동 중지 상태에서만 실행하며, 에너지와 작업 기준을 함께 초기화합니다. 물리적 엔코더의 누적값을 소급 변경하지 않습니다.

## 4. 일별 CSV와 에너지 환산

```csv
date,energy_kwh
2023-06-01,1024.5
2023-06-02,987.2
```

위 두 행은 형식 예시입니다. 실제 입력에는 최소 8일의 연속된 일별 자료가 필요합니다. 날짜 기준, 단위, 누락과 중복, 누적 계량값의 리셋 여부를 먼저 확인합니다. 건물급 계량 자료와 상위 배전계 자료를 중복 합산하지 않습니다.

예측 대상은 다음 날의 에너지 `kWh`이며 순간 전력 `kW`가 아닙니다. 실습에서는 명시한 환산 계수로 모형의 `Wh` 예산을 만듭니다.

```text
모형 예산 Wh = 일별 예측 kWh × 교육용 환산 계수 Wh/kWh
```

이 환산은 교육 시나리오의 정의입니다. 실제 건물의 시간별 부하나 설비별 전력 비중을 복원한 것이 아닙니다. 실물 운전은 실제 경과 시간으로 전력을 적분합니다. 짧은 모형 실습을 캠퍼스 하루의 실측 제어라고 해석하지 않습니다.

## 5. 로그를 읽는 법

- **명령:** LED 밝기 비율과 모터 출력 요구
- **관측:** INA260 전력·에너지, 엔코더 회전수·작업량, 장치 상태
- **운영 결과:** 예산 초과, 조명 요구 충족의 대체 지표, 목표 회전 달성 여부
- **오류:** 명령 만료, 계측 이상, 과전류, 회전 정체 등

PWM 명령은 조도나 실제 작업량과 다릅니다. LED의 서비스 평가는 현재 밝기 명령을 대체 지표로 사용하며, 실제 조도 검증에는 별도 센서가 필요합니다. 모터 작업량은 엔코더로 확인합니다. 소비전력이 줄었더라도 조명 요구나 목표 회전수가 줄었다면 동일 서비스의 절감 효과로 주장할 수 없습니다.

로그의 `power_w`·`rpm`은 수신된 관측이며 `next_command_id`·`next_led_duty`·`next_motor_duty`는 이를 본 뒤 반환하는 **다음 명령**입니다. `command_ack`는 장치가 마지막으로 확인한 명령 ID입니다. `led_applied_duty`·`motor_applied_duty`는 장치 로컬 로직의 PWM 설정값이며, 실제 물리 결과는 전력·회전수로 별도 확인합니다. 호환 필드 `led_duty`·`motor_duty`도 다음 명령을 의미합니다. 장치 경과 시각과 서버의 `received_at_utc`는 서로 다른 시계이므로 직접 차감해 통신 지연이라고 해석하지 않습니다.

전력 센서는 LED·모터 부하의 합계를 측정합니다. USB로 공급하는 ESP32 자체 전력은 이 계측 경계에 포함하지 않습니다. 에너지 예산은 운영 목표이며 퓨즈·배선 정격·드라이버 보호를 대신하지 않습니다.

실물 에너지는 장치의 경과 시각과 측정 전력을 사다리꼴 적분하여 계산합니다. 3초를 넘는 계측 공백은 임의의 전력으로 채우지 않으며 에너지 유효성이 낮아졌음을 표시합니다. 재부팅·시퀀스 역행·오래된 계측을 정상 관측처럼 사용하지 않습니다. 결과 내보내기에서는 유효성 상태와 누락 시간을 함께 확인합니다.

## 6. 검증과 수업

```bash
python -m unittest discover -s tests -v
```

하드웨어 없는 가속 비교실험은 다음과 같이 실행할 수 있습니다. 결과는 합성 DC 모형의 결과이며 작업 완료율을 함께 비교해야 합니다.

```bash
python experiment.py --seconds 180 --budget-wh 0.2 --output outputs
g++ -std=c++17 -Wall -Wextra -Werror -pedantic tests/native_firmware_test.cpp -o /tmp/tspai2-guards
/tmp/tspai2-guards
```

GitHub Actions에는 ESP32 코어 3.3.2, Adafruit INA260 1.5.3, ArduinoJson 7.4.2로 전체 보드 빌드를 수행할 설정을 포함했습니다. 설정 파일의 존재가 실제 CI 실행 성공을 뜻하지는 않습니다.
